# SpecRecs — System Plan

**Note:** this is the background and vision document. Where it differs from `agent-plan.md` on stack, repository layout or catalog, `agent-plan.md` is the working spec (for example, the pipeline is Node/TypeScript, not Python).

## 1. Project Goal

SpecRecs is a deterministic PC part recommendation system that helps users build or upgrade a desktop PC using:

- Current component pricing
- Reliable CPU and GPU performance data
- Hardware compatibility rules
- User goals and preferences
- Existing system specifications
- Upgrade-value analysis
- Retailer bundle pricing
- Optional local-store availability

The core recommendation engine should not depend on a live LLM. Recommendations should be reproducible, explainable, and based on structured rules and scoring.

An LLM may be added later only as an optional explanation layer, not as the decision-maker.

---

## 2. Core Design Principles

### Deterministic recommendations

The same inputs and data snapshot should produce the same recommendation.

### Explainable decisions

Every recommendation should be backed by measurable reasons such as:

- Performance improvement
- Price-to-performance
- Upgrade cost
- Compatibility
- Bundle savings
- Budget utilization
- User workload
- User style or size preferences

### Separate performance from pricing

Benchmark data answers:

> How fast is this component?

Pricing data answers:

> What does this component currently cost?

These should remain separate until the recommendation stage.

### Never trust a single listing

Retail prices should be treated as observations from multiple retailers and sellers.

Suspicious or extreme listings should be flagged before they can influence recommendations.

### Prefer cached data over live scraping

Retailers should be scraped periodically in the background.

The application should never wait for a retailer scrape when the user requests a recommendation.

## 6. User Input Model

The frontend should collect structured input rather than free-form text.

### Build Type

- New build
- Upgrade existing system

### Device Type

For the initial release:

- Desktop PC only

Laptop recommendations should be treated as a separate future feature because laptops require whole-system comparison rather than part compatibility.

### Primary Purpose

Initial categories:

- Gaming
- Gaming + streaming
- General use
- Productivity

Future categories may include:

- Video editing
- 3D rendering
- Software development
- Machine learning
- CAD

### Gaming Preferences

Where relevant:

- Target resolution
  - 1080p
  - 1440p
  - 4K
- Desired refresh rate
- Ray tracing importance

### Build Size

- Small → Mini-ITX
- Medium → Micro-ATX
- Large → ATX
- No preference

### Style Preferences

- RGB
- Minimal
- Clean
- Maximum price-to-performance
- No preference

Style should affect ranking only after hard technical constraints are satisfied.

### Budget

Collect:

- Maximum budget
- Optional preferred spend

This allows the recommendation engine to distinguish between:

> spend up to $1,500 if useful

and:

> try to stay around $1,200, but never exceed $1,500

### Location

Use coarse location only.

Preferred options:

- ZIP code
- User-selected nearby Micro Center location
- No local-store preference

Exact address data is unnecessary.

## 9. Benchmark Data

CPU and GPU benchmark spreadsheets should remain easy to maintain manually.

Recommended source files:

```text
cpu_benchmarks.csv
gpu_benchmarks.csv
```

These files should be imported into the normalized dataset during the build pipeline.

### CPU Performance Dimensions

At minimum:

- Gaming
- Single-thread
- Multi-thread
- Productivity

### GPU Performance Dimensions

At minimum:

- 1080p gaming
- 1440p gaming
- 4K gaming
- Ray tracing
- Productivity / compute where reliable data exists

Scores should be normalized so relative improvements can be calculated.

Example:

```text
RTX 3060     1440p score = 100
RTX 5070     1440p score = 176
```

Estimated relative improvement:

```text
(176 / 100) - 1 = 76%
```

The application should preserve benchmark source metadata so scores can be audited later.

## 10. Retailer Pricing Pipeline

Pricing should flow through several stages.

### Data source governance

Each source should have documented collection rules before it is enabled.

For retailer data:

- Prefer official APIs, feeds, or affiliate data where practical
- Review retailer terms and automated-access restrictions
- Keep scraper logic isolated per retailer so a source can be disabled without affecting the rest of the system
- Rate-limit collection and avoid unnecessary requests
- Record the source and collection timestamp for every observation

For benchmark data:

- Record benchmark source, methodology, date, and applicable licensing/attribution
- Avoid combining incomparable benchmark methodologies into one score without normalization
- Keep raw source values separate from SpecRecs's normalized scores

The recommendation engine should operate on normalized internal data and should not depend directly on any individual external source.

```text
Retailer
   |
   v
Raw Listing
   |
   v
Product Matching
   |
   v
Listing Validation
   |
   v
Accepted Price Observation
```

### Raw Listing Schema

```text
listing_id
retailer
retailer_sku
listing_title
url
price
original_price
seller
stock_status
store_location
timestamp
```

Never overwrite historical observations.

Historical data is useful for:

- Outlier detection
- Price trends
- Sale detection
- Debugging bad scraper behavior

## 11. Product Matching

Retailer listings must be mapped to canonical hardware.

Example:

```text
"GIGABYTE GeForce RTX 5070 Ti GAMING OC 16G"
```

should map to:

```text
GPU family: NVIDIA RTX 5070 Ti
variant: Gigabyte Gaming OC
```

Matching should use deterministic rules first:

1. Manufacturer
2. Product family
3. Model number
4. VRAM or capacity
5. Known retailer SKU mappings

A confidence score should be attached to the match.

Low-confidence matches should not automatically enter the recommendation dataset.

---

## 12. Price Sanity Checks

Scam, incorrect, used, marketplace, or malformed listings must not become the recommended price.

### Trusted Price Calculation

For each canonical product:

1. Collect recent accepted listings
2. Prefer reputable retailers and first-party sellers
3. Calculate the recent median price
4. Compare each listing to that expected range

Example:

```text
RTX 5070 Ti

Micro Center        $729
Newegg              $749
Best Buy            $769
Marketplace Seller  $249
Marketplace Seller  $1,849
```

Median trusted price:

```text
$749
```

The two marketplace listings should be flagged.

### Initial Heuristics

Example starting thresholds:

```text
price < 60% of recent trusted median
    -> suspicious_low

price > 160% of recent trusted median
    -> suspicious_high
```

These thresholds should be configurable rather than hardcoded throughout the application.

### Additional Validation Signals

Listings may be downgraded or rejected based on:

- Third-party marketplace seller
- Refurbished or used condition
- Incorrect product capacity
- Bundle incorrectly parsed as single component
- Accessory mistaken for component
- Open-box condition
- Missing product identifiers
- Suspicious title mismatch

### Price Confidence

Each accepted price can have a confidence level.

Example:

```text
Micro Center direct          1.00
Newegg direct                1.00
Best Buy direct              1.00
Known marketplace seller     0.75
Unknown marketplace seller   0.40
Flagged outlier              0.00
```

Only prices above a defined confidence threshold should influence recommendations.

## 14. Compatibility Engine

Compatibility should be evaluated before ranking.

### Hard Constraints

A candidate that violates a hard constraint is removed.

Examples:

- CPU socket mismatch
- Motherboard / CPU incompatibility
- DDR4 / DDR5 mismatch
- Motherboard form factor too large for case
- GPU too long for case
- CPU cooler too tall for case
- PSU wattage insufficient
- PSU form factor incompatible
- Unsupported CPU generation
- Required power connector unavailable

### Soft Constraints

Soft constraints affect score instead of eliminating the part.

Examples:

- Case style
- RGB preference
- Wi-Fi preference
- PSU efficiency
- Platform longevity
- Noise
- Aesthetics

Compatibility logic should live in one centralized module rather than being scattered through recommendation code.

---

## 15. Recommendation Engine

The core engine should follow:

```text
FILTER
  |
  v
SCORE
  |
  v
COMPARE
  |
  v
EXPLAIN
```

### Step 1 — Filter

Remove options that violate:

- Compatibility
- Maximum budget
- Availability requirements
- Required form factor
- User exclusions

### Step 2 — Score

Score remaining options according to user workload and preferences.

### Step 3 — Compare

Evaluate candidates against:

- Other candidates
- Current system
- Budget
- Bundle options

### Step 4 — Explain

Generate structured explanations from deterministic templates.

## 16. Workload Profiles

Recommendation weights should depend on use case.

Weights should be stored in configuration files so they are easy to tune.

Example gaming CPU profile:

```text
gaming performance        0.60
price/performance         0.20
platform longevity        0.10
power efficiency          0.10
```

Example productivity CPU profile:

```text
multi-core performance    0.50
single-core performance   0.20
price/performance         0.20
power efficiency          0.10
```

Example gaming GPU profile:

```text
target resolution score   0.60
price/performance         0.20
VRAM                      0.10
ray tracing               0.10
```

The exact weights should be validated with real examples rather than treated as permanent.

---

## 17. Value Metrics

The system should distinguish three concepts.

### Performance

```text
How fast is the component?
```

### Price-to-Performance

```text
performance_score / price
```

### Upgrade Value

```text
performance_gain_relative_to_current_system
-------------------------------------------
total_upgrade_cost
```

Upgrade value is especially important because it can identify when a technically faster component is still a poor upgrade.

---

## 18. Upgrade Recommendation Logic

Upgrade mode should use the current system as the baseline.

Example:

```text
Current CPU: Ryzen 5 5600X
Current GPU: RTX 3060
Budget: $600
Target: 1440p gaming
```

Potential options:

```text
CPU Upgrade
5600X -> 5700X3D
Cost: $180
Estimated gaming improvement: +11%

GPU Upgrade
RTX 3060 -> RTX 5070
Cost: $529
Estimated 1440p improvement: +72%

Platform Upgrade
5600X -> AM5 platform
CPU + motherboard + RAM
Cost: $510
Estimated gaming improvement: +17%
```

The engine can determine that the GPU upgrade produces the greatest improvement for the user's stated goal.

### Cascading Upgrade Cost

Always calculate the full cost of an upgrade path.

Example:

```text
CPU upgrade requires:
CPU             $300
Motherboard     $170
DDR5 RAM        $100

Effective upgrade cost = $570
```

This prevents misleading comparisons between drop-in upgrades and platform migrations.

---

## 19. Minimum Upgrade Thresholds

The system should avoid recommending small improvements unless there is another compelling reason.

Initial configurable ranges:

```text
< 15%   negligible
15–30%  marginal
30–60%  meaningful
> 60%   major
```

These labels should not be used as universal truths.

They are decision-support heuristics and may vary by workload.

A user with a very specific bottleneck may benefit from an upgrade even when overall performance gain appears small.

---

## 20. New Build Optimization

New-build mode should optimize the whole system.

Conceptually:

```text
maximize:
    weighted system utility

subject to:
    total cost <= budget
    all compatibility constraints
    availability constraints
    user preferences
```

A practical implementation does not need a sophisticated mathematical optimizer initially.

A staged heuristic is sufficient.

Example:

1. Reserve reasonable budget ranges by workload
2. Generate compatible CPU/GPU platform combinations
3. Fill motherboard, RAM, PSU, storage, case, and cooler
4. Apply bundles
5. Reject over-budget builds
6. Score remaining builds
7. Return top recommendations

---

## 21. System-Level Balance

Avoid simplistic CPU/GPU bottleneck percentages.

Instead, estimate whether a component is appropriate for the user's target workload.

For gaming, evaluate:

- Resolution
- Refresh target
- GPU performance
- CPU gaming score
- Expected GPU utilization class
- Current system baseline

The application should explain potential imbalance without pretending that a universal bottleneck percentage exists.

---

## 22. Recommendation Output

Return several recommendation categories rather than one opaque answer.

Suggested output:

### Best Fit

The build or upgrade with the highest overall score.

### Best Value

The option with the strongest performance gained per dollar.

### Performance Option

A faster option that remains within budget.

Each recommendation should display:

- Total price
- Performance estimate
- Improvement over current system
- Compatibility notes
- Bundle savings
- Price freshness
- Reason for recommendation

## 23. Explanation System

Do not require an LLM.

Use structured templates.

Example:

```text
The RTX 5070 is recommended because it provides an estimated
72% improvement in 1440p gaming performance over your RTX 3060.

At the current price of $529, it offers a stronger upgrade value
than replacing your CPU and platform.

Your existing Ryzen 5 5600X remains suitable for your target
resolution, so retaining it allows more of the budget to be
allocated to GPU performance.
```

The engine should output structured reason objects internally.

Example:

```json
{
  "type": "performance_gain",
  "component": "gpu",
  "old_value": 100,
  "new_value": 172,
  "percent_gain": 72
}
```

The UI converts these into readable explanations.

This makes future localization or optional LLM explanations straightforward.

## 32. Failure Handling

The system should degrade safely.

Examples:

### No current price

Use:

- Recent trusted price
- MSRP only as a clearly marked fallback
- Or exclude the product

### Suspicious listing

Flag and exclude it from recommendation calculations.

### Scraper failure

Continue using the previous valid dataset.

Never replace good data with an empty scrape.

### Unknown hardware

Allow manual entry where possible and mark performance comparison as unavailable.

### Partial current-system information

Return recommendations that can be safely evaluated and request only the missing fields required for unresolved compatibility checks.

## 36. MVP Definition of Done

The MVP is complete when the following end-to-end flow works reliably:

1. Scheduled jobs import maintained CPU/GPU benchmark data and collect current prices from the initial supported retailers.
2. Listings are matched to canonical products, validated, and suspicious prices are excluded from recommendation calculations.
3. The frontend loads a versioned normalized data snapshot without requiring a live recommendation backend.
4. A user can choose **New Build** or **Upgrade**, enter a budget and workload, and provide current CPU/GPU information when applicable.
5. The engine filters invalid choices, calculates performance, price-to-performance, and upgrade value, and returns reproducible ranked recommendations.
6. Upgrade recommendations include the full cost of any required platform changes rather than comparing component sticker prices alone.
7. Every recommendation includes a deterministic explanation, current price, price freshness, and relevant compatibility notes.
8. Fixed scenario tests verify that data or scoring changes do not silently produce unreasonable recommendations.
9. A failed or empty scrape cannot overwrite the last known-good dataset.
10. No live LLM, user account, or always-on backend is required for the core recommendation flow.

### MVP architecture summary

```text
Scheduled GitHub Actions
        |
        +---- Benchmark imports
        +---- Retail price collection
        |
        v
Normalization + validation
        |
        v
Versioned JSON snapshot
        |
        v
React / TypeScript frontend
        |
        +---- Compatibility engine
        +---- Recommendation engine
        +---- Explanation templates
        |
        v
GitHub Pages
```

The most important architectural boundary is:

```text
Performance data
    != Pricing data
    != Compatibility rules
    != Recommendation logic
    != Presentation
```

Keeping those concerns independent makes the system easier to test, audit, tune, and expand later to a database/API architecture without redesigning the recommendation model.
